## 3. 会议纪要

### 3.1 项目背景与目标确认

- 确认本项目为 **B2C 在线商城系统(含积分体系)**,覆盖商品展示、购物车、下单、支付、订单管理、评分与积分等核心电商功能,并提供管理员后台。
- 核心目标:
  - 为用户提供「浏览 → 加购 → 下单 → 支付 → 收货后评分 → 查看历史订单」的完整购物闭环;
  - 为管理员提供「商品上/下架、查看全部订单、调整全体用户积分」的运营能力;
  - 引入积分体系,支持消费得积分、购物抵现金、管理员发放/扣除。
- 目标用户分为普通用户(买家)与管理员两类。

### 3.2 角色与权限梳理

- 共三类角色:**游客(未登录)**、**普通用户**、**管理员(ADMIN)**。
- 游客仅可浏览商品列表与查看商品详情;登录后获得加购、下单、支付、评分、历史订单、积分等全部用户权限。
- 管理员在用户全部权限基础上,额外拥有商品上/下架与编辑、查看所有订单、调整任意用户积分的能力。
- 权限控制原则(已达成一致,作为开发红线):
  - 涉及个人数据(购物车、订单、积分)的接口必须校验登录身份;
  - 管理员接口必须校验角色为 ADMIN,防止越权;
  - 用户不能查看/操作他人订单与购物车。

### 3.5 积分体系设计评审

- **获得规则**:每支付完成 1 笔订单,按实付金额获得积分(默认 1 元 = 1 积分,比例可配置);管理员可手动发放。
- **使用规则**:支付时可使用积分抵扣,默认 100 积分 = 1 元(可配置);单笔抵扣上限不得超过订单金额的 50% 或可配置上限。
- **拦截规则**:积分余额不足或超抵扣上限时提示用户,不允许超额抵扣。
- **回退规则**:订单取消/退款时退回已获得或已使用的积分,标记为**可选实现**,列入 M7 评估。
- **限制规则**:积分仅限本人账户使用,不可提现、不可转账。
- **积分流水**:每次变动(获得/使用/管理员调整)生成一条流水,含流水号、用户 ID、变动类型(GAIN/SPEND/ADMIN)、变动数量(±)、余额快照、关联订单号、说明、时间。
- **结算优先级**已确认(共 5 步):
  1. 计算应付金额 = 订单小计 − 优惠;
  2. 用户输入拟使用积分(自动换算抵扣金额);
  3. 系统校验余额充足、抵扣 ≤ 应付金额、抵扣 ≤ 上限;
  4. 实付 = 应付 − 抵扣,同时扣减用户积分;
  5. 支付成功后按实付金额计算并发放本次获得积分。

### 3.6 非功能需求与数据模型确认

- 非功能需求(性能、一致性、安全、可用性、兼容性、可维护性)全部确认,重点强调:
  - 商品列表接口 < 500ms(1000 商品量级);
  - 下单扣库存、支付扣积分、积分发放等关键操作必须事务保证一致性;
  - 密码 BCrypt 加密、Token 鉴权、管理员角色校验、防越权、防 SQL 注入。
- 数据模型确认 7 个核心实体:user / product / cart_item / order / order_item / review / point_record。
- 订单商品项采用**快照**设计(下单时拷贝商品名称与单价),避免后续改价影响历史订单——架构师确认此方案可行。

### 3.7 技术栈与验收标准对齐

- 技术栈确认(与既有模板保持一致):
  - 前端:Vue 3 + Vite + Vue Router + Axios + Pinia,端口 5174,代理到后端;
  - 后端:Spring Boot 3.2.5 + Maven + Java 21,端口 8082;
  - 数据库:H2(开发期)/ MySQL,提供初始化 SQL 脚本;
  - 鉴权:轻量 JWT(HS256) + BCrypt。
- 验收标准共 7 条(购物闭环、购物车隔离、库存、积分、评分、管理员功能、权限安全)全部通过评审,作为各迭代验收依据。

## 4. 关键决策

1. 项目按「需求文档 v1.0」范围实施,需求状态为已确认。
2. 权限控制三原则(登录校验、ADMIN 角色校验、防越权)作为开发硬性要求。
3. 订单商品项采用快照方案,历史订单不受改价影响。
4. 积分抵扣上限默认「订单金额 50%」,获得/抵扣比例通过配置项管理,便于运营调整。
5. 积分结算按 5 步优先级顺序实现,支付成功后才按实付金额发放积分。
6. 本期按 M1–M7 顺序迭代,每期结束以对应验收标准做冒烟验证。
